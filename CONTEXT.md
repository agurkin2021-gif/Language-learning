# CONTEXT — рабочий контекст проекта

Этот файл — главный handoff для нового чата/агента. Перед любыми изменениями сначала прочитать его, затем сверить текущий код и последний GitHub Actions run. Не восстанавливать старые решения по памяти и не считать устаревший README источником истины по механике обновлений.

## 1. Что мы строим

Личное Android-приложение для изучения испанского с русским интерфейсом.

Основная идея:
- пользователь добавляет испанские слова и устойчивые выражения с русским значением;
- карточка остаётся в изучении, пока пользователь сам не нажмёт «Знаю»;
- освоенные карточки сохраняются в SQLite, но отдельный экран «Освоенное» скрыт; встроенный ИИ видит их вместе со всеми карточками в изучении;
- данные хранятся локально и должны переживать перезапуск и обновление APK;
- есть библиотека испанских рассказов и проигрыватель системным TTS;
- приоритет голоса: es-AR, затем es-MX, затем другой испанский;
- есть скорость речи, пауза, повтор, режим по одному предложению и непрерывный режим;
- в будущем рассказы должны генерироваться помощником на основе освоенной пользователем лексики. Эта генерация пока НЕ подключена. Граница для неё уже заложена через StoryGenerator / Store.mastered().

Главный продуктовый принцип: приложение должно быть простым. Нельзя заставлять пользователя ходить по GitHub, файловому менеджеру, вручную искать APK или нажимать одно и то же много раз.

## 4. Требование к обновлению

Пользовательское требование жёсткое:

Обычный будущий сценарий должен быть:
1. пользователь нажимает «Обновление» один раз в основном приложении;
2. приложение само проверяет версию;
3. само загружает подписанный APK;
4. передаёт установку штатному Updater;
5. обновление завершается без браузера, GitHub, файлового менеджера и повторных ручных нажатий.

Допустим только ОДИН переходный системный шаг, если Android требует его для закрепления отдельного Updater как установщика/владельца последующих обновлений. Нельзя выдавать этот переходный шаг за обычный сценарий каждой версии.

## 5. Почему прежнее самообновление признано ненадёжным

Была длинная серия попыток обновлять основное приложение самим собой.

Ключевые проблемы:
- в старой версии кнопка «Обновление» фактически запускала только фоновую проверку, поэтому пользователю казалось, что ничего не происходит;
- затем были добавлены скачивание и PackageInstaller, но на реальном телефоне потребовались повторные нажатия;
- были лишние промежуточные состояния/подтверждения и повторные попытки;
- на эмуляторе сценарий мог проходить, а на физическом телефоне Android/HyperOS отменял установку;
- конкретно переход с установленной 0.1.45 на 0.1.48 на телефоне завершался сообщением об отмене обновления, хотя эмуляторный тест был зелёным;
- из этого сделан важный вывод: зелёный эмуляторный тест НЕ является доказательством работы на конкретном HyperOS-устройстве.

Также старые APK в ранней истории использовали временную debug-подпись. Подписанный постоянным ключом APK не может обновить APK с несовместимой подписью поверх. Нельзя удалять приложение с нужными пользовательскими данными только ради смены подписи.

## 6. Текущая архитектура обновления

В проект добавлено отдельное приложение-обновлятор:

package: `ru.spanish.learning.updater`

Основные файлы:
- `updater/src/main/java/ru/spanish/learning/updater/UpdaterActivity.java`
- `updater/src/main/java/ru/spanish/learning/updater/InstallResultReceiver.java`
- `updater/src/main/AndroidManifest.xml`

Основное приложение сохраняет свою логику проверки/валидации в `AppUpdater.java`, но рабочая целевая схема — передача установки отдельному Updater.

Updater:
- получает кандидата на обновление;
- проверяет пакет/версию/подпись;
- работает через Android PackageInstaller;
- использует отдельный package и должен стать installer of record после однократно подтверждённого перехода;
- после этого последующие обновления должны выполняться тем же Updater без второго системного подтверждения.

Основное приложение должно вызывать Updater с одной пользовательской кнопки. Повторные нажатия не должны создавать параллельные installation sessions.

## 7. Что именно доказал run №65

В `updater-installer-test` на Android 14 проверена последовательность:

1. Устанавливается базовая версия основного приложения.
2. Устанавливается отдельный Updater.
3. Updater получает разрешение REQUEST_INSTALL_PACKAGES.
4. Первая переходная версия ставится через Updater с одним допустимым системным подтверждением.
5. После этого проверяется, что `ru.spanish.learning.updater` стал installer of record.
6. Затем запускается основное приложение.
7. Нажимается именно кнопка обновления в основном приложении.
8. Следующая версия ставится через Updater.
9. Второго системного подтверждения быть не должно.
10. Проверяется, что installer of record по-прежнему Updater.

Результат этого теста: SUCCESS.

Отдельно `self-update-test` подтверждает корректность PackageInstaller-пути, versionCode и сохранение локальных данных на эмуляторе.

Это доказывает архитектуру на Android 14 в CI. Это НЕ доказывает поведение конкретного физического HyperOS-телефона.

## 8. Что ещё НЕ подтверждено

Не подтверждён полный сценарий на физическом телефоне пользователя с HyperOS.

До такой проверки нельзя писать или говорить:
- «на телефоне точно работает»;
- «проблема окончательно решена»;
- «больше системных окон точно не будет».

Корректная формулировка до физического теста: CI и Android 14 emulator проходят; HyperOS остаётся отдельной приёмкой.

## 9. Что делать дальше по обновлению

Не возвращаться к серии случайных переписываний self-update.

Следующий порядок:
1. Сверить последнюю ветку и последний успешный CI.
2. Убедиться, что опубликованы и основной APK, и Updater APK с постоянной подписью.
3. Проверить метаданные `phone-builds`, сертификаты, versionCode и package IDs.
4. На физическом телефоне выполнить ОДИН переход на отдельный Updater.
5. После закрепления Updater выпустить следующую тестовую версию.
6. Проверить: одно нажатие «Обновление» в основном приложении → новая версия установлена → нет браузера/файлового менеджера/повторного «Установить».
7. Проверить сохранность карточек, освоенного архива, рассказов, позиции и настроек.
8. Только после этого считать проблему обновления закрытой.

Если физический тест снова не проходит, сначала получить фактическую причину: PackageInstaller status, install source / installer of record, разрешение unknown sources, подписи, versionCode и HyperOS restriction. Не делать новую архитектуру наугад.

## 10. Канал публикации и подпись

Публичный канал обновлений: ветка `phone-builds`.

Основной APK: `SpanishLearning.apk`.

Публикация подписанного APK зависит от Repository Actions Secret `ANDROID_SIGNING_CONFIG`.

В Git нельзя добавлять:
- keystore;
- пароли;
- приватную конфигурацию подписи.

В репозитории допустим только публичный отпечаток сертификата и открытые метаданные.

При каждом выпуске сохранять:
- тот же `applicationId`;
- совместимый постоянный сертификат;
- возрастающий `versionCode`.

APK перед установкой должен проверяться по SHA-256, package, versionCode и подписи.

## 12. Правило для новых слов и изображений

Любое новое встроенное слово или выражение добавляется только комплектом:
- испанский текст;
- русский смысл;
- корректный тип/категория;
- локальный SVG в `app/src/main/assets/card-images/`;
- тот же asset и запись в `card-assets/card-images/` / `index.json`;
- SVG должен сохранять текущий формат 256×256 и общий визуальный стиль приложения.

Нельзя выпускать новое встроенное слово без картинки. `CardAssetTest` обязан проверять полный стартовый словарь и падать при отсутствующем SVG, дублированном испанском слове, коллизии ключа или неверном формате SVG.

Если пользователь просит «добавь такие-то слова», это по умолчанию означает: добавить слова и сразу создать для каждого подходящий ассоциативный SVG в существующем стиле, без отдельного напоминания.

## 13. Направление дальнейшей разработки приложения

После стабилизации обновлений:
- довести UX карточек до устойчивого состояния без прыжков/случайных повторных действий;
- сохранить локальную простоту приложения;
- не ломать уже работающие карточки, архив, SQLite и TTS;
- затем подключать генерацию адаптированных рассказов по освоенной лексике;
- генерация должна использовать реальные освоенные карточки, а не фиктивный шаблон;
- до подключения провайдера отдельно решить авторизацию, стоимость, приватность и способ запуска генерации пользователем.

Главный приоритет сейчас: сначала довести обновление на физическом телефоне до предсказуемой схемы «одна кнопка → обновлено», не потеряв пользовательские данные.

## 14. Скрытый архив и полный словарь для встроенного ИИ

Решение пользователя: убрать кнопку «Освоенное» с экрана карточек. Пользователь тренирует карточки по одной, без списка уже изученных слов. Кнопку «Знаю» оставить; данные mastered в SQLite не удалять, чтобы сохранялся прогресс.

Контекст встроенного ИИ при каждом запросе содержит все карточки — слова и устойчивые выражения, пользовательские и стартовые, как освоенные, так и ещё изучаемые. Никакого ограничения «первые 300». Передавать испанский текст, русский смысл, категорию и статус освоения; отделять освоенные от изучаемых. При создании сказок учитывать освоенное в первую очередь. Полный перечень не отображать в обычном интерфейсе.

Настройки, обновление через отдельный Updater, озвучка испанского через 1 секунду после появления и мелкий номер версии под карточкой должны остаться без изменений.


## 15. Удержание слова в испанской сказке

В режиме прослушивания и в полном тексте сказки испанское слово можно удерживать пальцем: приложение само определяет границы одного слова без Android-выделения и без диалога подтверждения. Текст сказки неизменен. Нажатая форма, включая неправильные и спряжённые глаголы, добавляется в обычные карточки для изучения. Повторное удержание уже изучаемого слова не создаёт дубль; если слово ранее помечено «Знаю», оно возвращается в изучение.

Для частых неправильных глаголов связывается словоформа с исходным глаголом, но исходное написание сохраняется (например, querés, fui). При отсутствии надёжного определения значения карточка содержит испанское предложение и его русский перевод как контекст, без выдуманной дословной расшифровки. Для известных основ используется их существующий SVG; иначе создаётся офлайн SVG с символом книги. Новые слова находятся в «Все слова» (неклассифицированные — категория 0), отсутствующие в остальных фильтрах до классификации. Сведения доступны встроенному ИИ через Store.vocabulary(). Существующий механизм обновления и сохранения прогресса не меняются.
